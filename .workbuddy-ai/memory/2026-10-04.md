## Round 37 — Path A is proven feasible: Rust can bind D3D11 on WP8.1

The user rejected the C#-replays-Rust-draws design outright ("C# rendders the game? forget it —
does Rust render directly?"). Direction chosen by the user: **Option A — Rust talks to D3D11
itself**, i.e. a real Rust renderer instead of a drain that C# repaints.

Before committing weeks to it, I ran a two-stage feasibility probe. Both stages live in
`rust-wp81/d3d11-rs-probe/` and are driven by `build.ps1` (self-contained; auto-locates the
`wp81-compat` rlib).

### Stage 1 — does the `windows` crate bind D3D11 for this target?

`src/lib.rs` uses the real, unpatched **`windows` 0.62.2** (vendored in the managed cargo registry)
with `Win32_Graphics_Direct3D11` / `Dxgi` / `Direct3D` / `Foundation` features.

**It compiles for `thumbv7a-pc-windows-msvc`** — `core`, `std`, `compiler_builtins` and the whole
`windows` stack build. So the bindings themselves are not the blocker.

But `tools/dylib_imports.py` (NEW — maps each raw-dylib *import descriptor member* to the DLL it
names; the archive member is literally named after the DLL, which is why a naive listing looks
mangled) shows what that crate drags in:

```
    8  api-ms-win-core-handle-l1-1-0.dll
   23  api-ms-win-core-winrt-error-l1-1-0.dll
   17  api-ms-win-core-winrt-l1-1-0.dll
    8  combase.dll
    5  d3d11.dll
   12  d3dcompiler_47.dll
   12  d3dcsx.dll
    9  dxgi.dll
   33  kernel32.dll          <-- not on WP8.1
    4  ntdll.dll             <-- not on WP8.1
   26  oleaut32.dll          <-- not on WP8.1
    4  rpcrt4.dll            <-- not on WP8.1
    4  user32.dll            <-- not on WP8.1
```

The `kernel32`/`oleaut32`/`combase`/`rpcrt4`/`user32`/`ntdll` descriptors come from
`windows-core`'s own `link!` uses (ABI plumbing), **not** from the D3D11 entry points. That is the
finding that shapes the design: the `windows` crate is usable for *compiling* the logic, but its
own binding must not be the one that reaches the linker.

### Stage 2 — bind D3D11 by hand, to WP8.1's own module names

`src/direct.rs`: no `windows` crate at all. Just `extern "system"` + `#[link(name = "d3d11.dll")]` /
`#[link(name = "dxgi.dll")]`, COM vtable calls done by hand (`#[repr(C)] { vtbl: *const *const
usize }` + a slot fetch), plus the CRT-free entry point (`_fltused`, `DllMain`,
`_DllMainCRTStartup`) that `prpr-port` and `link-probe` also define.

Result — **21,504-byte ARM DLL, import table exactly:**

```
wp81d3d11rs.dll imports 2 libraries:
     OK  dxgi.dll   <- ships on WP8.1 (proven by the kit's ARM import lib)
     OK  d3d11.dll  <- ships on WP8.1 (proven by the kit's ARM import lib)
CHECK OK
```

**Proof the two DLLs are on the phone:** `Windows Phone Kits\8.1\lib\ARM\` ships
`d3d11.lib`, `dxgi.lib`, `d3dcompiler.lib`. And the C++ probe (`wp81d3d11.dll`) already reached the
Adreno 225 through `d3d11.dll` **on a real device**. So this is not desktop-only reasoning.

The 31 `LNK2019` std symbols (`GetEnvironmentStringsW`, `NtCreateFile`, `NtReadFile`,
`CreatePipe`, `SetStdHandle`, `GetUserProfileDirectoryW`, …) that show up when linking the probe
standalone are **exactly the set `wp81_std_patch.py` + `wp81-compat` already handle** — linking the
compat rlib in, as `build-port.ps1` does, closes every one of them. Nothing new is needed.

### What this means

**Rust rendering itself on WP8.1 is possible.** The architecture that follows:

- Bind D3D11/DXGI **directly** (`d3d11.dll`, `dxgi.dll`) — hand-rolled externs, not the `windows`
  crate's `link!`, because the crate leaks kernel32.
- Reuse the existing `wp81-compat` + patched-std machinery for the std surface, unchanged.
- `check_imports.py` gained a `PRESENT_ON_PHONE` set (`d3d11.dll`, `dxgi.dll`,
  `d3dcompiler_47.dll`) so the gate still fails on a genuine leak while accepting these. The gate
  text is now "every import is an API set **or** a DLL the WP8.1 kit links against".
- Next: shaders. D3D11 needs **HLSL/DXBC** where prpr's GL path has GLSL, so the shader set has to
  be rewritten (or precompiled offline) — that is the remaining large piece, not the binding.

### Traps confirmed again

- `-Zbuild-std=std,panic_abort` **must be quoted** in PowerShell (array-literal parse failure).
- The host `LIB` must point at `VC\lib\amd64` + `Win Kits\8.1\um\x64` or the x64 build *script*

## Round 38 — verified against the device's own OS image + the kit's ARM import libs

User supplied (a) their exact OS build **8.10.12393.890** (Lumia 925 / RM-910, WP8.1 GDR1) and
(b) a full signed FFU: `D:\925\RM-910\RM910_3051.50009.1424.0004_RETAIL_apac_prc_200_04_438106_prd_signed.ffu`
(1.84 GB). Goal: turn "the SDK says d3d11.dll is present" into "the phone's d3d11.dll exports
exactly what my Rust binding calls."

### FFU structure (now fully decoded — `tools/ffu.py`)

```
0x00  u32  0x20                     signature block size
0x04  'SignedImage '                magic (PKCS#7 blob follows at 0x20)
0x10  u32  0x80   *4096 = 0x80000   catalog offset   <-- the key field
0x14  u32  0x800c
0x18  u32  0x6e1  *4096 = 0x6e1000  image offset
0x1c  u32  0x6db40 *4096 = 0x6db40000  image size ( == file size − header )
```

There is **no GPT in the FFU**. At `0x80000` sits the **ImageFlash catalog** — plain INI text
(`[FullFlash]` description, `[Store] SectorSize=512 MinSectorCount=20971520`, 28 × `[Partition]`,
then a `Package:` list of all 60 packages — incl. `Qualcomm.QC8960.direct3dum`, the Adreno UMD).
The text ends ~`0x4be0` into the catalog; after it, at catalog+`0x800`, comes a **binary block map**:
a flat array of 16-byte records `(partitionId, 1, 0, lba4k)` — one record per 4K block, `lba4k` in
4 K units (`lba4k * 8` = 512-byte sector). Not needed for the import-name verification below, but
it *is* how you'd carve MainOS later.

Partition table (sectors, 512 B each):

| Name | Total | Used | FS | Align |
| --- | --- | --- | --- | --- |
| DPP/MODEM_FSG/SSD/SBL1-3/UEFI/RPM/TZ/WINSECAPP + BACKUP_*/UEFI_*NV | small | 0 | – | – |
| PLAT | 16384 | 11932 | FAT | – |
| EFIESP | 131072 | 19384 | FAT | 64 MB |
| MODEM_FS1/2 | 6144 | 0 | – | 64 MB |
| MMOS | 165504 | 157024 | FAT | – |
| **MainOS** | 4928128 | **3237888** (1.54 GB) | **NTFS** | 8 MB |
| Data | rest | uses all space | NTFS | 8 MB |

`tools/ffu.py list` prints this; `tools/ffu.py carve <Partition> <out>` is written but its
sequential-block-walk assumption is not yet validated against the real block map.

### The verification that actually matters

I did **not** end up needing to carve MainOS. The authoritative same-source check is the WP8.1
kit's own **ARM import libraries** — the exact thing `link.exe` validates against.
`C:\Program Files (x86)\Windows Phone Kits\8.1\lib\ARM\` (and, identical symbols, the Win8.1
SDK at `Windows Kits\8.1\Lib\winv6.3\um\arm\`) ships:

- `d3d11.lib` — **87** symbols; entry points: `D3D11CreateDevice`, `D3D11CreateDeviceAndSwapChain`,
  `D3D11CoreCreateDevice`, `D3D11CoreCreateLayeredDevice`, …
- `dxgi.lib` — **23** symbols; entry points: `CreateDXGIFactory`, `CreateDXGIFactory1`,
  **`CreateDXGIFactory2`** (bonus — not in the Win8.1 SDK docs), `DXGID3D10*`, `DXGIGetDebugInterface1`.
- `d3dcompiler.lib` — **61** symbols; **`D3DCompile`**, `D3DCompile2`, `D3DCompileFromFile`,
  `D3DReflect`, `D3DDisassemble` …

**Every entry point my Stage-2 Rust binding declares is present, by name, in the phone's ARM
import lib.** ✔ `D3D11CreateDevice` ✔ `D3D11CreateDeviceAndSwapChain` ✔ `CreateDXGIFactory1`.

Consequences:
1. Path A's import surface is **confirmed correct for this device**, not merely plausible.
2. **Shaders can be compiled on-device** — `D3DCompile` is available in `d3dcompiler.lib`
   (`d3dcompiler_47.dll` is already in `check_imports.py`'s `PRESENT_ON_PHONE`). So the HLSL set
   does **not** have to be precompiled offline; a runtime `D3DCompile` path is the fallback, and
   offline DXBC is the fast path. This removes the "shaders are the blocker" caveat.

### How to read an import lib's symbol names

`ar` members: the first member (`/`) is the **big-endian** linker symbol index; `/1` is the
little-endian one. Its symbol offsets are *not* self-relative, so the reliable move is to scan each
member body for NUL-delimited `[A-Za-z_]\w+` runs (that's how the lists above were obtained).
`!<arch>` magic is **8** bytes (`!<arch>\n`) — `d[:7]` silently mismatches.

### Files

- `rust-wp81/tools/ffu.py` (new) — FFU header + ImageFlash catalog + partition table reader
- `/tmp/ffu_catalog.txt` — the full catalog text for this image

### Traps

- The FFU header offsets (`0x10`, `0x18`, `0x1c`) are in **4 K units**, not bytes; `0x1c*0x1000`
  reconstructs the exact file size. `0x6e1000` (image offset) is all `0xFF` — the image stream is
  not contiguous from there; the block map governs placement.
- The `EFI PART` hits at `0x108980` etc. are **not** GPT headers (fields are garbage) — they are
  ARM code bytes inside partition payload. Do not model the FFU as a GPT disk: it has no GPT.

## Round 39 — Stage 1 verified on real D3D11; three binding bugs found

Because the phone was not connected, I built a **desktop verification harness**
(`src/bin/hostcheck.rs`, host-only, behind `#![cfg(all(windows, not(target_arch = "arm")))]` and
built solely via `cargo build --bin hostcheck`) that compiles the **same** `direct.rs` / `renderer.rs`
for `x86_64-pc-windows-msvc` and runs the whole Stage 1 path against the real D3D11 runtime:
`create_device -> swapchain (hidden HWND) -> RTV -> build_pipeline -> clear -> Draw(4,0) -> Present`.

It now prints `=== ALL STAGE 1 CHECKS PASSED ===`. It caught **three bugs that would each have
crashed on the phone** — none was a compile error:

1. **`ComPtr::method` read the vtable one level short.** `ComPtr.vtbl` is the *object pointer*
   (`*vtbl` is the vtable, `(*vtbl)[n]` the method, `vtbl` is `this`). The old
   `(*self.vtbl.add(n)) as *const T` treated the object pointer as the vtable, so every call read
   one slot early. Correct:
   `let vtable: *const usize = *self.vtbl; transmute_copy(&*vtable.add(n))`.
2. **Every `ID3D11DeviceContext` slot was off by 4.** The base is `ID3D11DeviceChild`, so the first
   context method is slot **7**, not 3. (`ID3D11Device` derives straight from `IUnknown`, so *its*
   slots do start at 3 — the two interfaces do not share an offset. All `ID3D11Device` slots in the
   file were already correct.) Authoritative values, extracted from `Windows Kits\8.1\Include\um\
   d3d11.h` declaration order: VSSetConstantBuffers 7, PSSetShaderResources 8, PSSetShader 9,
   PSSetSamplers 10, VSSetShader 11, DrawIndexed 12, Draw 13, Map 14, Unmap 15, PSSetConstantBuffers
   16, IASetInputLayout 17, IASetVertexBuffers 18, IASetIndexBuffer 19, IASetPrimitiveTopology 24,
   OMSetRenderTargets 33, OMSetBlendState 35, RSSetState 43, RSSetViewports 44, UpdateSubresource 48,
   ClearRenderTargetView 50, Flush 111.
3. **`Map` was missing the `MapFlags` argument.** `Map(resource, subresource, D3D11_MAP MapType,
   UINT MapFlags, out)` — the out-param was landing in `MapFlags`, so `Map` returned `E_INVALIDARG`
   (`0x80070057`). Added `pub type D3D11_MAP = UINT;` and a `0` MapFlags at every call site.

**Rule this establishes:** a wrong vtable slot is a crash or a bogus HRESULT, never a compile error
— so anything that touches `direct.rs` must be re-run through `hostcheck` before it goes near the
phone.

### Link plumbing the harness needed (and why it does not affect ARM)

- `#[link(name = "d3d11.dll")]` makes MSVC ask for **`d3d11.dll.lib`**, which the Win8.1 SDK does
  not ship (it has `d3d11.lib`). The `#[link]` attributes were therefore **removed** from
  `direct.rs`; the libraries are named by the linker. `build.ps1` already passed the ARM libs by
  hand, and the host path names them in `.cargo/config.toml` under
  `[target.x86_64-pc-windows-msvc]` (`-L` the Win8.1 `um\x64` **and** VS11 `VC\lib\amd64`, then
  `-l d3d11 -l dxgi -l d3dcompiler -l user32`; both `-L`s are needed — the SDK dir alone leaves
  `msvcrt.lib` unresolvable).
- `build.ps1` now builds with **`--lib`**, and `Cargo.toml` declares `[[bin]] name = "hostcheck"`
  explicitly, so the ARM target never tries to link the harness's x64 `user32.lib`.

The ARM artifact is unchanged in size (**12,800 bytes**) and still imports exactly
`d3d11.dll` + `dxgi.dll` + `D3DCOMPILER_47.dll`; `check_imports.py` = OK. WP ARM head and Win8.1
head both build green; the `.appx` (39 entries) carries the corrected DLL
(sha256 `b1fc7f4790b8540d…`).

### New: `RustStage1Page` — the actual acceptance test

A dedicated page (`RustStage1Page.xaml(.cs)`) hosting a real **`SwapChainPanel`** and handing its
native pointer to Rust. C# only does three things: pass the panel + pixel size, call

### The instrumentation that made the failure legible

First on-device run: `stage=2` with a useless `hr=0x00000000`, because `renderer.rs` returned early
without recording anything. Fixed by adding a **trace slot**: `create_swapchain_for_panel_traced`
records `(step, hresult)` at each of ~6 failure points, and `wp81_rs_sc_step_name()` returns an
ASCII name for the step. The phone log then said, precisely:

```
stage=123 hr=0x887A0001  swapchain-step=CreateSwapChainForComposition (code 23)
```

So: **D3D11 device created on the phone from Rust ✓; IDXGIDevice ✓; adapter ✓; IDXGIFactory2 ✓;
only the composition swapchain creation failed.** `0x887A0001` = `DXGI_ERROR_INVALID_CALL`.

### The actual bug: `CreateSwapChainForComposition` takes `DXGI_SWAP_CHAIN_DESC1`

I had been passing the **legacy `DXGI_SWAP_CHAIN_DESC`**. `IDXGIFactory2::CreateSwapChainForComposition`
requires **`DXGI_SWAP_CHAIN_DESC1`**, which is a different struct: it drops `RefreshRate`,
`ScanlineOrdering`, `OutputWindow` and `Windowed`, and adds `Stereo`, `Scaling` (`DXGI_SCALING_*`)
and `AlphaMode` (`DXGI_ALPHA_MODE_*`). Passing the legacy struct reads every field from the wrong
offset → `DXGI_ERROR_INVALID_CALL`, which looks exactly like "unsupported on this driver" but is
really a **layout mismatch**. This is the single most misleading failure mode hit so far.

Added `DXGI_SWAP_CHAIN_DESC1` + `DXGI_SCALING_*` + `DXGI_ALPHA_MODE_*` to `direct.rs`, and the
creation now tries four descriptor shapes in order (FLIP_SEQUENTIAL x2 premultiplied →
FLIP_SEQUENTIAL x2 ignore → DISCARD x1 ignored → SEQUENTIAL x1 ignored), recording the accepted
index in `wp81_rs_sc_variant()` so the log names the working shape.

### Export-table trap, again

New `#[no_mangle]` entry points **silently did not appear** in the DLL: `build.ps1` carries an
explicit `/EXPORT:` list and `#[no_mangle]` does not export from a staticlib. Symptom is a smaller
DLL than expected (12,800 vs 13,312) and a `DllImport` that throws only at the first call. Every
new entry point must be added to `build.ps1`'s list.

Also: `CompositionTarget` needs `using Windows.UI.Xaml.Media`, and WP8.1's `CoreDispatcher` has
`RunAsync` (not `BeginInvoke`).

The DLL is now **14,336 bytes**, 12 exports, still importing exactly d3d11/dxgi/d3dcompiler_47.

## Round 41 — the fault isolated to one call; both panel interfaces confirmed

### What the log proved

The bisect + `DispatcherTimer` watchdog finally gave a readable trace. The tail:

```
RustRenderer.vtable: readable slots = 32
RustRenderer.vtable: 0=0x71ED3825 ... 24=0x71F00D21 25=0x71EDE461
RustRenderer.vtable: slot3(GetParent)=0x71EFD1C5 slot24(CreateSwapChainForComposition)=0x71F00D21
RustRenderer.factory: IsCurrent=-1 QI(IDXGIFactory2) hr=0x00000000
RustStage1: tick -> 13 (swapchain: CreateSwapChainForComposition)
RustRenderer.Bisect: step limit=16 -> calling native  [next: IDXGISwapChain::GetBuffer(0) ...]
   <-- nothing after this; the process dies here
```

Conclusions, each with its evidence:

- **`readable slots = 32` and slot 24 = `0x71F00D21`** → the vtable is NOT short, and slot 24 is a
  real code pointer. Slot number / IID / factory pointer are all **correct**.
- **`QI(IDXGIFactory2) hr=0x00000000`** → the object really is an `IDXGIFactory2`.
- **`limit=16` is the run that dies**, and it dies after tick 13 → the fault is inside
  `CreateSwapChainForPanel` at/after `CreateSwapChainForComposition`. It **hard-faults** instead of
  returning `DXGI_ERROR_INVALID_CALL`, which is the signature of an **unimplemented DXGI 1.2
  entry**, not of a wrong slot.

### The `IsCurrent=-1` red herring (and the real bug in my own probe)

`IsCurrent=-1` looked alarming (not a valid BOOL) but was **not evidence**: the `limit=13` run
returns *before* the `record_factory_probe` call, so the static was still at its `-1` initialiser.
The probe was dead code during the bisect. **Moved the probe to run *before* the `limit_is(13)`
stop**, so `limit=13` now genuinely exercises slot 13, with its own tick (17).

### Fixes / changes this round

1. **Descriptor variants reordered** — `DISCARD x1`, `SEQUENTIAL x1`, then the two
   `FLIP_SEQUENTIAL x2` shapes. FL 9.3 forbids the flip model (needs ≥10.0), so the FL-9.3-safe
   effects are tried FIRST. If the flip model is the trigger, the call now returns a clean HRESULT
   and `wp81_rs_sc_variant()` names the accepted shape instead of killing the process.
2. **Both panel interop interfaces are now tried** on attach: `ISwapChainPanelNative`
   (`F92F19D2-3ADE-45A6-A20C-F6F1EA90554B`) then `ISwapChainBackgroundPanelNative`
   (`43BEBD4E-ADD5-4035-8F85-5608D08E9DC9`). Both have `SetSwapChain` at slot 3. Which one answered
   is recorded in `wp81_rs_panel_iface()`.
3. **`SwapChainBackgroundPanel` IS usable on WP8.1** — proven by compiling against the real WP8.1
   reference set (`tools/probe_api.py --file`): instantiable, has `Name`, assignable to
   `Page.Content`. Confirmed in the kit's own `windows.ui.xaml.media.dxinterop.h`.
   (IIDs read from that header; the plan previously carried a wrong IID for `ISwapChainPanelNative`
   — `63aad0b8-…` — now corrected.)
4. **Two bisect stops now separate the last two suspects**: `limit=13` = run the probe, stop before
   slot 24 (dies → probe guilty); `limit=18` = skip the probe, stop before slot 24 (clean → slot 24
   guilty). `limit=18` is also accepted by the `None` early-return path in `lib.rs`.
