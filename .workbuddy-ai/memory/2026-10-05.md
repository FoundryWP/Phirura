## R55 — the four new symptoms: registry cap, alpha, touch guard, perf

User reported: judge-line effects now correct, but notes/UI/text gone; no touch response; lag; the
result page blank. Root causes, all found in code + one log:

1. **`TEX_SLOTS = 128` was the whole "images don't display" story.** The log line
   `GameCreate(190, …) -> 0 (Ok) | 128 registered, 66 dropped` says it outright: 194 registrations
   were attempted, the table filled, and 66 textures were silently refused - a dropped texture is
   invisible, never an error. 90 synced textures already totalled ~36.7 MiB against a 32 MiB byte
   budget, so *both* limits were live. Raised `TEX_SLOTS` to 512 (28 B/entry = 14 KB) and
   `TEX_MAX_BYTES` to 64 MiB. Confirmed fixed on device: **`119 registered, 0 dropped`**.
   Added `wp81_texture_drop_info(index)` (reason/id/w/h/bytes/held/cap) so a refusal names itself,
   and `PrprPort.TextureSummary()` now prints it; the frame-stats line carries it every second.
2. **The regression: `VertexStride` was not moved with `PortVertex`.** Adding the vertex alpha made
   the native record 36 B while `PrprPort.ReadVertex` still read 8 floats at a 32 B stride - so
   `PortVertex.a` stayed 0, the renderer's "nothing to draw" guard fired for *every* geometry
   triangle, and notes/UI/text vanished while judge lines (a different command kind) kept drawing.
   Fixed `VertexStride = 9*4` and the `a` read at off+32. **`WireLayoutOk()` existed but was only
   called from the unused `DrainSelfTest`, so it never fired** - now asserted at startup and printed
   every run: `wire layout ok=True cmdStride=56/56 vertexStride=36/36`.
   *Lesson: when a record gains a field, the stride constant and the field reader are a pair; the
   only thing that catches a miss is asserting the size at startup.*
3. **Touch: the guard, not the pipeline.** New logging showed
   `touch down … rust=True started=False` - the presses arrived and were dropped by
   `if (_paused || _finished || !_started) return;`. `_started` is set only by the C# chart path's
   `StartPlayback`, so in phira mode it is *never* true. Replaced with an `InputLive` property:
   `_rustCreated` on the Rust path, `_started` on the chart path.
4. **Lag, three independent causes:** `PushRustTouches` duplicated the drain+draw+present so every
   frame rendered twice; `FillPortTriangle` leaked an undisposed `CanvasGeometry` per untextured
   triangle per frame (78 fps → 26 fps over ten minutes); and `PrprPort.ReadF` called
   `BitConverter.GetBytes` per field, i.e. tens of thousands of 4-byte allocations per frame.
   Fixed all three, plus reused the drain buffers instead of allocating three arrays per frame, and
   folded the two triangles of a quad into one `DrawImage` (which also stops semi-transparent notes
   being double-darkened).
5. **Log rotation threw away the beginning.** `AppLog.Append` deleted and recreated the file past
   256 KB, so a >11-minute run lost the chart load and the gameplay - the part worth having. Now
   keeps the tail with a rotation marker.

**`tail-log.ps1` (new) = the "runtime log" answer.** WP8.1 has no attached debugger, so following
the log means polling `ISETool ts` and printing the delta. Traps it handles: the destination must not
already exist (a failed attempt left its directory behind, so every retry failed the same way - a
fresh name *per attempt* is required), and **it reads `appxfolder:Temp`, not Local**.

### Why the hit effect cannot appear at all (R56, root-caused, not yet fixed)

The hit effect is not a sprite on the command stream - it is `prpr::particle`'s emitter, and that
module **drives miniquad's `Context` directly** instead of going through macroquad's draw API:

```
prpr/src/core/resource.rs:577  emit_at_origin -> self.emitter.emit_at(..)
prpr/src/particle.rs:789       Emitter::draw -> get_internal_gl(); setup_render_pass; perform_render_pass; end_render_pass
prpr/src/particle.rs:728-736   perform_render_pass: ctx.apply_bindings(&self.bindings);
                                                     ctx.apply_uniforms(&Uniforms{ mvp, .. });
                                                     ctx.draw(0, index_count, instance_count)   // instanced quads
prpr/src/particle.rs:717       self.bindings.vertex_buffers[1].update(ctx, &self.gpu_particles[..]);
```

Every one of those is a **no-op in the shim** - `rust-wp81/shims/miniquad/src/lib.rs` says so itself:
*"Every method is a no-op: the C# renderer owns the real device. `prpr::particle` drives this
sequence directly... but what they do is recorded elsewhere - the draw commands come through
`macroquad::QuadGl`."* That "recorded elsewhere" was never implemented for this path:

* `Context::apply_bindings` / `apply_uniforms` / `draw` - all empty (lib.rs:498-524).
* `Buffer::update<T>(&self, _ctx, _data)` - **empty, the particle instance data is discarded**
  (lib.rs:764); `Buffer::new`/`immutable` keep only `len` (lib.rs:748-753).

So nothing about a hit effect ever enters the port's `Cmd` arena, and the C# renderer has no way to
know a particle exists. **It is not a regression and no renderer fix can reach it.**

**The fix** (self-contained, ~one round): make the miniquad shim *record* the particle pass instead of
dropping it - `Buffer::update` stores the instance bytes, `apply_bindings` remembers the bound
texture, `apply_uniforms` keeps the MVP, and `Context::draw` expands the instances into quads and
pushes `Cmd::Geometry` (texture + vertex colour, positions through the recorded MVP). Same change
would also unlock `JudgeLineKind::Paint`, which is the other raw-render-pass path.

**Also confirmed:** `emit_at_origin` early-returns when `!self.config.particle`, so the particle
switch in `RenderConfig` must be on as well (it is - the port never turns it off).

### R57 — the particle plan, and the blocker that changes it

I proposed "make the shim record the pass" and went to implement it. **The blocker is the MVP**:
`prpr/src/particle.rs:730` calls `ctx.apply_uniforms(&shader::Uniforms { mvp, emitter_position,
local_coords })`, and the shim's signature is `apply_uniforms<T>(&mut self, _uniforms: &T)` -
**generic, so the shim cannot name `T` and cannot read `mvp`**. The only ways round it are a
`type_name`+transmute hack (fragile) or re-deriving the projection. So "record the pass" is not the
cheap route I estimated.

**What the pass actually contains, now fully extracted** (this is what makes the alternative small):

```
prpr/src/particle.rs: GpuParticle { pos: Vec4, uv: Vec4, data: Vec4, color: Vec4 }   // 64 B instance
  pos.xy = particle position, pos.z = rotation (rad), pos.w = size
  uv.xy  = atlas offset,      uv.zw  = atlas size      (rewritten per frame by the animation update)
  color  = per-particle RGBA
shaders/particles.glsl:
  transformed = rot2d(inst_pos.z) * attr_pos.xy * inst_pos.w + inst_pos.xy   (+emitter_position if local_coords)
  gl_Position = _mvp * transformed
  texcoord    = attr_uv * inst_uv.zw + inst_uv.xy
fragment: texture2D(texture, texcoord) * in_attr_inst_color
```
So a particle is exactly a **rotated, atlas-sourced textured quad with a per-vertex colour** - which
the port already draws (`Cmd::Geometry` + the new `TryDrawPortQuad`). `self.config.texture` is a
`Texture2D`, so the port texture id is available without any binding capture.

**The route that avoids the blocker entirely:** give `Emitter::draw` a
`#[cfg(target_arch = "arm")]` branch that iterates `self.gpu_particles` and emits each as a quad
through macroquad's own draw API (or a small shim helper), instead of the raw `Context` sequence.
No uniform extraction, no binding capture, no cross-crate plumbing - `macroquad`'s path already
carries the camera and the texture id, and the desktop harness (`x86_64`) keeps the GL path because
the cfg is off there. **`prpr/src/particle.rs` is the file to touch** (it is a build input, not
read-only, despite living under `phira-main/`).

Still needs one device round for three conventions I cannot settle from the source alone: the
rotation origin macroquad uses, the y sign (`emit_at_origin` negates y), and whether the particle
positions are already screen pixels (they look like it - `world_to_screen`). **Nothing was edited
this turn; the repo is clean.**

### R57 (cont. 2) — the particles DO reach the renderer. Proof, and the counter trap.

The first counter read `particles=0` and looked like a failure. It was a **counter-design** mistake,
not a renderer one, and two rounds were spent on it. What settled it:

```
rust: particles: draws=1860 seen=848 pushed=848 quads=0
```

* `pushed` counts what `draw_port_particles` actually handed to `push_sprite_quad` - **848**, so the
  path is live and the quads reach the command stream.
* `quads` reads `LAST_SPRITE_QUADS`, published at the end of `encode()`. It is 0 because it describes
  **the last frame only**, and particles are emitted per hit - a sampled second with no live particle
  is legitimately 0. A per-frame counter cannot answer "does this ever happen"; a cumulative one can.
* `seen`/`pushed` stop growing once the hits stop, which is the same fact from the other side.

**`texture: None` was a real bug and is fixed.** `Resource` builds `emitter_square` without an image
on purpose - it is the *solid-coloured* emitter and it fires **four particles per hit**, while the
textured `emitter` fires one. The first version returned early on `texture: None` and so dropped most
of the effect. `tex: 0` is the port's no-texture id and the shell already draws it as a flat fill
from the vertex colour, which is what the GL path does with no image bound.

**Also fixed this round (both were my own regressions from R55):**
* `TryDrawPortQuad` now returns false for **axis-aligned** quads, so glyphs and UI rects go back to
  the exact bounding-box path. Sending every glyph through the affine path was needless risk - a
  wrong matrix there is garbled text, not a stretched sprite.
* Touch logging is rate-gated (200 ms) and `WriteSync`'s wait is 500 ms instead of 3 s. Every log
  line costs six blocking WinRT calls (Local + temp mirror), the appends are one serialised chain,
  and `WriteSync` runs on the UI thread once a second - so a finger burst could block the render loop
  for seconds. That is the "picture froze but the game kept running, and a native button woke it up".

### R58 — skewed hold, latency, and the font corruption ruled out of one suspect

* **Skewed/stretched hold appearing behind a short hold, on long-press.** `TryDrawPortQuad` consumed
  six indices and assumed they were one quad. When a batch holds a hold's body *and* its head, the
  window can name five or six distinct vertices - and the uv extremes then come from two different
  shapes, so the affine map is built from one shape's corners to another's and draws a slanted copy.
  Fixed with a strict guard: the six indices must name **exactly four** distinct vertices, or the
  call falls back to the bounding-box path.
* **Touch latency.** The real cost is the frame time, and the largest single item in it was
  `EnsurePortTextures`: a sweep of **three native calls per registered texture** every frame (~119
  textures on the 190 chart => ~360 calls/frame) purely to ask "did anything change", on a frame that
  also replays ~150 draw commands. Now polled every **third** frame - chart art never changes after
  load and the glyph atlas only has to be current before the text using it is read, so a 60 ms lag is
  invisible while the calls come straight off the frame time.
* **Font corruption is NOT the atlas being re-created.** Instrumented it:
  `texNew=1 texRebuilt=2` for a whole run - the glyph atlas is created once and rebuilt twice, never
  repeatedly re-created, so the "new id, stale carrier" theory is dead. Still unexplained; the next
  suspect is the *delta upload* (`SyncPortTexture` + `PaintPortBand`) racing the draw, since it is
  driven by new glyphs and therefore by touching.
* **Particles confirmed working again**: `pushed=882` in the first second of gameplay, then flat -
  they exist only while notes are being hit, which is also why every sampled second between hits
  reads `quads=0`.

### R60 — two more of my own regressions, both found and fixed

**Startup white blocks, then text appearing a moment later = the texture-poll gate.** Gating
`EnsurePortTextures` unconditionally to every third frame starved the carriers: a texture registered
on frame N had none for up to three frames, and **a geometry batch whose texture has no carrier falls
back to a flat fill - which is a white block**. During a load the first frames are seconds apart, so
"up to three frames" was seconds. Fixed by polling **every frame while the registry is still growing**
(tracked by comparing `TextureCount()` with the last sweep) and gating only once it is stable.
Verified: `noCarrier=0` on the first frame of the run.

**Hit effects landing off the judge line = the model matrix applied twice.** `Resource::emit_at_origin`
puts the particle position through `world_to_screen`, which **is** the model
(`model_stack.last()`), and the shader it replaced applies only the camera. `push_sprite_quad` then
called `transform::project`, which applies `MODEL` *and* the camera - so every particle was
double-transformed. Added `transform::project_world` (camera only) and switched `push_sprite_quad` to
it. **The rule: `project` is for values in world space, `project_world` for values that already have
the model folded in.**

**Occasional freeze: reduced, not eliminated.** The rate-gated touch log and the 500 ms `WriteSync`
wait removed the reproducible case, and the poll gate now skips the sweep only when the set is
stable. Still under investigation; nothing in the log so far points at it.

### R65 — `home.rs` reached, and two precise symptoms on it

### R67 — SOLVED: dead buttons / missed fast taps = the touch RELEASE was being overwritten

**My y-flip hypothesis above was wrong.** The user reported that home's buttons *do* show their
pressed feedback - so the hit-test works and the coordinate space is fine. What was missing was the
**release**.

`PushRustTouches` (and the C# judge path's copy of the same loop) did:

```csharp
if (_justStarted.Contains(kv.Key)) { touch.Phase = TouchPhase.Started; }
else if (touch.Phase == TouchPhase.Started) { touch.Phase = TouchPhase.Stationary; }
```

A press **and** a release can both land between two frames - that is what a fast tap *is* - and
`_justStarted` still holds the id on the frame that pushes it. So `Started` was forced over the
`Ended` the pointer handler had just written, and **the engine saw a finger go down and never come
up**. A UI button drew its pressed look and never clicked; a fast tap on a note was never released. A
held finger was unaffected, which is exactly why drag and long-press worked while everything else
looked dead.

Fixed by letting a resolved `Ended`/`Cancelled` pass through untouched - `_justStarted` now only
*upgrades* a touch that is still logically down. Applied to both loops.

**Lesson worth keeping: "the button reacts but does nothing" is a RELEASE problem, and "nothing
reacts at all" is a hit-test problem. Those two need completely different investigations, and I
spent two rounds on the wrong one.** The one detail that separated them was the user noticing the
pressed feedback.

### R68 — `_active` was growing without bound (logged), and it likely blocks the click

The release fix alone did not revive the buttons. A fresh log then showed the real defect:

```

touch up id=56 ... remaining=23
touch up id=67 ... remaining=33        // 3 seconds apart
```

`remaining` is `_active.Count`, so **the finger table only ever grew** - the engine was being handed
twenty to thirty-three simultaneous fingers. A button that believes other fingers are still down

the increasingly erratic judging.

Cause: retirement depended *entirely* on `_toRemove`, so any release that did not land there left its
finger in the table for the rest of the session. Fixed with a second sweep in `PushRustTouches` that
retires **anything already in `Ended`/`Cancelled`**, whatever the bookkeeping says (`_retire` is a
reused list, not a per-frame allocation).

**Not yet confirmed on device** - the user has to press a button and check `remaining=` stops growing.
If it does not, the release genuinely never fires and the next thing to instrument is which of
`PointerReleased`/`PointerCanceled`/`PointerCaptureLost` the platform actually raises per tap.

**Result of that check (R69): partly helped, not fixed.** The log says two things:

* **`scenes=1` for all 444 samples** - the app is on `home.rs` and stays there. The screen is reached;
  the buttons simply do not act, so this is not a navigation problem.

`PointerCaptureLost` never fires, so it is not the path to hang retirement on. And the release count

**So the C# side is now clean and the gap is further in.** Everything measured on the shell side is

### R71 — PRIME SUSPECT FOUND: `QuadGl::get_projection_matrix()` returned `Mat4::IDENTITY`

Traced the middle of the chain by reading rather than instrumenting, and it is wired correctly:

* `push_touch` queues into `PENDING`; `macroquad::input::touches()` returns that queue **raw** - which
  is why note/drag judging works. `host.rs:643/680` clear it per frame, so it cannot fill up.
* `judge.rs:372` `repeat_all_miniquad_input` **is** called from `on_new_frame` and does fill `TOUCHES`
  via `for_each_pending`, so the events do reach the UI's store.
* `Handler::touch_event` pushes the position **raw**; the conversion happens in `Judge::get_touches`
  through `touch_transform`, which uses `prpr::ext::get_viewport`. The shim returns `None` from both
  `get_viewport` and `get_active_render_pass`, so that falls through to
  `(0, 0, screen_width(), screen_height())` - **correct**.

**The defect is one line away from all of that:**

```rust
// rust-wp81/shims/macroquad/src/lib.rs, QuadGl
/// The projection `prpr::ui` composes its transforms against.
pub fn get_projection_matrix(&self) -> Mat4 { Mat4::IDENTITY }   // <- was
```

`prpr::ui` derives its **hit-test rectangles** from this matrix, while the shell draws the same
geometry through its own camera. An identity here puts the rectangles in a **different space from the
pixels the touches arrive in**, so every rectangle misses while everything still *looks* correctly
placed on screen - the exact signature of "the button shows its pressed look and never fires", and of
drag notes (no rectangle involved, judged from the raw list) still working.

Fixed to the y-down pixel -> NDC ortho that `touch_transform` already assumes:
`Mat4::orthographic_rh(0, w, h, 0, -1, 1)` from `screen_width()`/`screen_height()`.

**Deployed and launched; not yet confirmed.** The thing to watch: if the buttons now act, this was it.
If instead the *layout* has moved, that proves `prpr::ui` also draws through this matrix and the two
sides have to be made consistent rather than one of them corrected.

**Result: neither.** The buttons are still dead **and the layout did not move** - so `prpr::ui` does
not draw through `get_projection_matrix()`, and correcting it changed nothing either way. Reverted in
effect (the ortho is harmless and more correct, so it stays, but it is not the cause).

### R73 — ROOT CAUSE: the shim's clock was frozen at 0, so home's intro never unlocked the buttons

Two things had to be fixed before the measurement could even be seen:

* **The diagnostic was gated on `particle_diag(0)`**, which only advances while a chart plays - so on
  the home screen, exactly where the UI bug is, the line was never written. Re-gated on a frame
  counter. **An instrument that is silent where the fault is worse than no instrument**, and it cost
  the user two rounds of tapping for nothing.
* Measured: `pending=0..2`, `replayed` climbing 57 -> 338. **Both halves work.** The events reach
  prpr's `TOUCHES`, so the loss is inside the UI.

Then, reading `home.rs`:

```rust
// phira/src/page/home.rs:416

    self.btn_play_3d.touch(touch, t);
    if self.btn_play.touch(touch, t) { ... }     // the action
```

**Every button on the page sits behind that gate**, and `rt` is *real time*. And:

```rust
// rust-wp81/shims/macroquad/src/lib.rs
static MICROS: AtomicU64 = AtomicU64::new(0);
pub fn set_now_micros(us: u64) { MICROS.store(us, Ordering::Relaxed); }   // NO CALLER ANYWHERE
pub fn now_secs() -> f64 { MICROS.load(...) as f64 / 1e6 }
```

`set_now_micros` **has no caller** - there is no miniquad event loop to call it, because the shell owns
the loop - so `get_time()` was **0.0 for the life of the process**. The intro transition never
progressed, `char_screen_p.now(rt)` never fell below `1e-2`, and the touch handler **returned before
reaching any button**. Nothing was broken: the animation that unlocks the buttons never ran.

**Fix:** `clock::advance_secs(dt)`, called from `wp81_game_frame` with the `dt` the shell already
passes, **before** `host::frame` (which is where the scene reads the time).

This also explains the whole shape of the bug: the page *draws* correctly (a static start state), the
notes judge fine (they use the shell's `_phiraTime`, not this clock), and my
`get_projection_matrix()` change did nothing at all (unrelated).

**Generalisation worth keeping: on this port, anything prpr derives from `get_time()`/`get_uptime()`
was frozen at 0 from the start. That is a whole class of bugs, not one.**

**Follow-up (R74): the clock fix alone did not revive the buttons.** `dt` is non-zero and clamped to
<= 0.05 by `RenderPhiraFrame`, so the clock does advance now, and the scene's own `t` advances
(`rust: the_main: frame=... t=...`). So either the gate is not what blocks the touch, or `rt` does not
track the clock. Instrumented rather than guessed again: a two-slot `macroquad::dbg` channel, set from
`home.rs`'s `touch` with `(rt, char_screen_p.now(rt))` and printed by the frame entry point as
`gate=`/`thr=` (x1000). `phira` cannot log directly - `prpr_port` depends on it, not the reverse, and
`tracing` has no subscriber here - so parking floats in macroquad is the only route out.

### Why it "freezes so easily" - one concrete cause found and fixed

`PrprPort`'s Rust-to-log callback used **`AppLog.WriteSync`**, which **waits up to 500 ms for the disk
flush**, and Rust calls it from **`wp81_game_frame` - the render thread**. The periodic lines
(`rust: the_main: frame=...` every second, plus the new diagnostic) therefore stalled the frame loop
**once a second, by design**. Changed to `AppLog.Write` (queued, non-blocking); the only thing given up
is that the last line can be lost on a hard kill, which was already true of every other line.

The other two contributors, both fixed earlier: a touch burst queueing blocking file I/O (now rate
gated at 200 ms, `WriteSync` wait 3 s -> 500 ms), and the one-time texture sync during load.

### R79 — reading the pump: `load_info` CANNOT park, so the earlier conclusion was wrong

Two things read, both of which invalidate R78's "the executor stopped" reading:

* **`macroquad::load_file` is synchronous** - it just calls the asset hook and returns
  (`shims/macroquad/src/lib.rs:2989`), so it cannot park. But note `prpr::fs::load_info` calls
  **`fs.load_file(":info")`**, the *`FileSystem` trait* method, not this one - a different function
  that reads through `ExternalFileSystem`/`Dir`.
* **`app::poll()` restores the future correctly** (`lib.rs:729`): it takes the future out of the cell
  to avoid a re-entrant borrow, polls it, and on `Pending` puts it back (line 750). The only path that
  drops it is `Ready`, which is a completed application. So the executor is not losing the future.

**And the pump loop explains the 80 ms** (`host.rs:530`):

```rust
for i in 0..BOOT_POLLS {
    if macroquad::app::reached_first_frame() { return Ok(()); }
    let poll = macroquad::app::poll();      // only i == 0 is logged
    ...
}
```

Only `i == 0` is logged, so **"poll 0 -> Pending" says nothing about how many polls followed** - the
loop simply exhausted `BOOT_POLLS` without `reached_first_frame()` ever turning true. It is a tight
poll loop, not a frame-paced one, and the successful run took **9469 ms** for the same boot, so the
difference is that the future now makes no progress across polls.

**Next probe, and it is the one that matters:** count the polls and log the future's progress, plus
which `FileSystem` read `Data::init` is inside when it stalls. `fs.load_file` is the trait method -
instrument *that*, not `macroquad::load_file`, which was the wrong function to suspect.

### R80 — ROOT CAUSE: `tokio::task::spawn_blocking` never completes on WP8.1

The probe settled it in one run:

```
rust: Data::init: load_info -> entering prpr::fs::load_info
rust: phira: poll 0 -> Pending (parked, booting)
rust: phira: boot_phira -> -2: phira never reached its first frame after 64 polls
```

`-> entering` printed and `-> returned` **never did**, so the future was stuck inside
`prpr::fs::load_info` - and the pump only gets **`BOOT_POLLS = 64`** polls before giving up. (That
number is why the earlier "poll 0" reading was misleading: only `i == 0` is logged, so it says nothing
about how many polls followed.)

`prpr/src/fs.rs:90`, `ExternalFileSystem::load_file`:

```rust
let mut file = self.0.open(path)?;
tokio::task::spawn_blocking(move || { let mut res = Vec::new(); file.read_to_end(&mut res)?; Ok(res) }).await?
```

`spawn_blocking` hands the closure to tokio's **blocking pool**, which **creates threads on demand** -
and this target will not give this DLL working threads (`std::thread` aborts with `0xC0000409` here).
When a blocking thread cannot be created the task never runs and **the await never resolves**.

**Fixed by reading inline** (the file is local; there is no async I/O to preserve).

**Verified on device:**
```
Data::init: load_info -> returned from prpr::fs::load_info
GamePage: phira boot -> 0 in 8961 ms, stage 7 (phira ready)
rust: input: pending=0 replayed=1 -> 5 ... gate=12346 thr=0 now=3
```

**This one line explains four separate reports**: the boot that parked at stage 6, the chart cover that
never loaded (same function, same read), the intermittency (it depends on whether a blocking thread
happens to get created), and `replayed` freezing. **Generalisation: any `spawn_blocking` (or anything
else needing a thread) on this target is a hang, not an error. `std::thread` aborts; the tokio
blocking pool silently never runs.**

### R81 — the dead buttons are now a per-button problem, not a plumbing one

Device report after R80: **the resource-pack button works**, the rest do not. That is decisive:

* `home.rs:437` `btn_respack` sits **inside the same `if self.char_screen_p.now(rt) < 1e-2` block** as
  `btn_play`, `btn_event`, `btn_msg` and `btn_settings` (lines 417-451). So the gate is **open** -
  confirmed independently by the probe (`thr=0`, and `0 < 1e-2`).
* Therefore the touch store, the replay, the hit-test **mechanism** and the click path are all
  **proven working**. Everything upstream of the individual button is now ruled out by evidence, not
  by argument.

What is left is per-button: the **rectangles**. A `DRectButton` hit-tests against a rect computed in
the layout pass, while what the player sees is drawn through the port's camera - if those two disagree
for some buttons and not others, exactly this pattern appears (one button works, its neighbours do
not). `btn_respack` works, so the mechanism is sound and the fault is in where the others think they
are.

**Next step, and it is small:** log each button's rect next to the touch position for a single tap.
That says immediately whether the rects are misplaced, and in which direction - which is also the
answer to "the hit rect and the drawn position disagree". Note `btn_play` and `btn_event` use
`with_delta(-0.01)` / `with_elevation(0.002)` while `btn_respack` also uses `with_elevation(0.002)`,
so the constructors are not the difference.

**Mechanism found (`prpr/src/ui.rs:184`, `DRectButton::contains`):**

```rust
if let Some([a, b, c, d]) = self.pts { ...point-in-quad... } else { false }
```

The hit-test is against `pts`, the quad the **layout** pass stores. A button whose rect is **offset**
from where it is drawn is therefore only reachable by a **large** target - which is exactly the report
("respack works, its small neighbours do not"), and it is the same signature as gameplay (drag, a
full-width target, worked while precise taps missed). **So the touch position reaching `prpr::ui` is
offset from the drawn position, and the size of the target decides whether it still lands.**

Instrumented to measure it rather than guess: `macroquad::dbg` widened to four slots, `home.rs`'s
`touch` parks `(rt, char_screen_p.now(rt), touch.position.x, touch.position.y)`, and the frame line
prints the last two as `tx=`/`ty=`. Comparing `tx/ty` with where the finger actually landed (the shell
logs the DIP position, x2 for pixels) gives the offset directly - and its direction names the fix.

**MEASURED (R82): the touch reaches `prpr::ui` with position (0, 0).**

```
rust: input: ... gate=55728 thr=0 tx=0 ty=0
GamePage: touch down id=166 at 473.5,258.5      <- the finger, DIP = (947, 517) px
```

So the hit-test compares **(0,0)** against every rect and only a button containing the top-left corner
can ever hit - which is why "respack worked" was a coincidence of its rect, not a working path.

`tx=0` **exactly** is the tell, not a small number: a NaN printed through the integer log (`as u32`)
becomes 0, and the only place a position is rewritten is `Judge::touch_transform`
(`prpr/src/judge.rs:382`):

```rust
touch.position = vec2(
    (p.x - vp.0 as f32) / vp.2 as f32 * 2. - 1.,
    ((p.y - (screen_height() - (vp.1 + vp.3) as f32)) / vp.3 as f32 * 2. - 1.) / (vp.2 as f32 / vp.3 as f32),
);
```

Divide by `vp.2` (and by `vp.2 / vp.3`) - **a degenerate viewport turns every position into NaN**, and
`prpr::ext::get_viewport` falls back through `get_active_render_pass()` to `screen_width()/height()`,
both of which the shell must have set (`host.rs:822`). **If the shell has not reported a size by then,
the fallback is `(0,0,0,0)` and every touch becomes NaN** - which also matches the intermittency.

**Next probe:** log the position at the FFI entry (`push_touch`, as received) next to the value in the
store. That separates "the shell sends garbage" from "the transform destroys it" in one run. Also log
`screen_width()`/`screen_height()` there - if they are 0, that is the whole bug.

### R83 — DECISIVE: the position is good entering the DLL and (0,0) by the time the UI sees it

```
rust: input: ... gate=15493 thr=0 tx=0 ty=0 px=719 py=519 pn=29 sw=1280 sh=768
```

* `px=719 py=519` - the position at the FFI boundary, after the shell's DIP->px conversion. **Correct**
  (the finger was at DIP ~360,260, i.e. 719,519 px). **The entire C# side is now proven correct.**
* `tx=0 ty=0` - what `home.rs`'s `touch` sees. **Wrong.**
* `sw=1280 sh=768` - `screen_width()/height()`. Fine, so the `prpr::ext::get_viewport` fallback is not
  degenerate *at the point this line is printed*.

**So the loss is inside the DLL, between `wp81_game_touch` and `prpr::ui`.** That leaves exactly three
places, all in `prpr`: `Judge::get_touches`/`touch_transform` (`judge.rs:382`, the only code that
rewrites a position), `Judge::on_new_frame` (`judge.rs:367`, the only filler of `TOUCHES`), and
`Handler::touch_event`. **`tx=0` exactly is the tell: a NaN printed through an integer log reads as 0,
and `touch_transform` divides by `vp.2`.**
